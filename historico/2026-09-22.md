# Snapshot - 2026-09-22

Sessão disparada por um e-mail da Vercel avisando que o time gratuito `marcelo-di-foggia-juniors-projects` bateu 100% do "Function storage" (10GB do Hobby). Investigação começou pelo painel de billing/uso pra achar qual projeto era o vilão, depois virou fix de verdade no cotor-ia.

## 🎯 O que foi feito hoje

### 1. Auditoria de uso do time na Vercel (via CLI + painel)
- `vercel project ls` no time: 16 projetos.
- Painel de Usage (breakdown "Projects" por métrica, `?view=Projects`): **Functions Storage 13,76GB/10GB** (137%, o que gerou o e-mail) — `cotor-ia` respondia por **9,89GB (72%)**, `trader-os` por 2,8GB (20%), resto irrelevante.
- **Deployment Storage 5,48GB/10GB** (55%, ainda não bateu o teto): `califorce` respondia por **4,07GB (74%)** — projeto parado há 122 dias.

### 2. Limpeza do `califorce` (fora deste repo, mas decidido nesta sessão)
- Confirmado: sem domínio customizado (só `califorce.vercel.app`).
- `vercel remove califorce --yes` — projeto removido por completo (todos os deployments). Marcelo confirmou: parado há meses, sem motivo pra manter.

### 3. Causa raiz do estouro de Functions Storage no cotor-ia
- `find` nos binários do Prisma: `node_modules/@prisma/client/runtime/` tinha os engines WASM de **todos** os provedores (mysql/sqlserver/sqlite/cockroachdb/postgresql), tanto `.js` quanto `.mjs`, + `libquery_engine-darwin-arm64.dylib.node` (18MB, só usado em dev local no Mac) — mesmo o `schema.prisma` usando só `provider = "postgresql"`.
- `@img/sharp-*` (libvips + wasm32, ~26MB) também sendo tracejado em toda rota, sem necessidade — a Vercel tem infra própria de Image Optimization, não precisa de `sharp` bundlado nas funções do usuário.
- Medi via script Node lendo os `.nft.json` do `.next/server` (soma do tamanho de todos os arquivos referenciados por rota, que é literalmente o que a Vercel empacota por função): **2,43GB por deployment**, batendo com a estimativa (9,89GB / ~3 deployments retidos ≈ 3,3GB cada).
- Também achado (mas não confirmado como causa real): comentário já existente no `next.config.ts` reconhecia que a HOME do usuário tem `package-lock.json` próprio e pode ser inferida como "monorepo root" pelo Next — só corrigido pro Turbopack (`turbopack.root`), não pro tracing de produção. Testei isolado: **não mudou o tamanho local** (2,43GB antes e depois). Mantido mesmo assim por ser boa prática documentada e não ter custo.

### 4. Fix aplicado (`next.config.ts`)
- `outputFileTracingRoot: process.cwd()` — mantém o tracing restrito à pasta do projeto (não muda tamanho local, mas evita comportamento imprevisível caso o ambiente de build da Vercel resolva o lockfile de forma diferente do Mac local).
- `outputFileTracingExcludes: { "/*": [...] }` — exclui dos bundles de função:
  - `@prisma/client/runtime/*mysql*`, `*sqlserver*`, `*cockroachdb*`, `*sqlite*` (só postgresql é usado)
  - `.prisma/client/*darwin*` e `@prisma/engines/*darwin*` (binário nativo de dev, nunca usado em produção Linux)
  - `@img/**` (sharp completo)
- **Resultado medido:** soma de todas as rotas caiu de **2,43GB → 0,551GB (-77%)**.

### 5. Validação antes de declarar pronto
- Testei um caminho errado primeiro: setei `output: "standalone"` temporariamente pra simular o pacote de deploy localmente — descobri que o modo standalone usa outro mecanismo de cópia de `node_modules` que **não respeita** `outputFileTracingExcludes` (ainda trazia `@img/sharp-*`). Revertido — não é o teste certo; o que importa é o `.nft.json` por rota, que é o que a Vercel usa de fato pra montar cada função.
- `next build` + `next start` local: home 200, rota autenticada 401 (esperado), `/opengraph-image` (usa `next/og`) 200, sem erro no log.
- Commit `06c516f`, push, `vercel deploy --prod` → `Aliased: https://cotor-ia.vercel.app`.
- **Testado AO VIVO em produção** (não só local): home 200, `/opengraph-image` 200, `/sitemap.xml` 200 (bate no Prisma via ISR), `/api/templates` 401 (auth-gated, correto), `/entrar` 200. `vercel logs` sem erro.

## 📝 Decisões técnicas importantes
- `outputFileTracingExcludes` é a ferramenta certa (documentada pelo próprio Next.js) pra cortar arquivos que o file tracing inclui por engano/excesso — usar de novo se aparecer outro projeto com Function Storage inflado.
- Prisma sem driver adapter bundla engine de **todos** os provedores de banco por padrão, mesmo com um só configurado no schema — vale revisar isso em qualquer outro projeto do Marcelo que usa `@prisma/client` puro (TraderOS já usa `@prisma/adapter-pg`, então é bem menos afetado — 2,8GB de Functions Storage mesmo com Prisma 7).
- `output: "standalone"` NÃO é um bom proxy pra testar o que a Vercel vai empacotar numa função — usa lógica de cópia própria, diferente do tracing por rota que a Vercel usa de verdade.
